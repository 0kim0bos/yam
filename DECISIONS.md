# yam Decision Baseline

Every `yam` change is evaluated against honest proof, progressive depth, security-first guidance, modular skills, and useful non-specialist insight.

## Fixed Questions

1. What needs concrete evidence before completion?
2. What should stay selective or low-context?
3. What can be removed to keep the core obeyable?
4. What should `yam` keep fast by default, and what should deepen deliberately?
5. What security surface could a non-specialist miss?
6. What should the user learn from this change?
7. Which external references informed the judgment, and how were those ideas reworked into yam style?

## Keep

### Strict Proof

- Truthful completion language.
- Risk escalation.
- Bounded verification.
- Fake versus real distinction.
- Runtime/process proof only when explicitly requested.

### Modular Skills

- Skills-first structure.
- Selective install.
- Low-context and no-hooks path.
- Token optimization.
- Project-specific rules instead of global bloat.

### Progressive Core

- Short core.
- Few route names.
- Minimal context.
- Rules the model can actually follow.
- Fast momentum without pretending simple work is always enough.
- Depth growth when the user's understanding, project risk, or product quality benefits from it.

### Beginner Insight

- Explain changed behavior in plain language.
- Name the code area touched and what it is responsible for.
- Separate implementation facts from judgment.
- Always close with remaining tasks or useful improvements.

### Security First

- Treat auth, payment, DB, secrets, permissions, deployment, and public release as first-class risk surfaces.
- Prefer read-only inspection before sensitive writes.
- Do not hide destructive or production-like risk behind convenience.
- Make safer defaults visible to the user.

## Reject

### From Strict Proof

- Mandatory hooks.
- Mandatory Team or subagent proof.
- Always-on tmux/proof lifecycle.
- Heavy memory systems for ordinary edits.

### From Modular Skills

- Full install by default.
- Giant catalog context.
- Hook runtime by default.
- Too many always-on rules.

### From Progressive Core

- Under-verification.
- Vague quality rules.
- No route structure for risky work.
- Lightweight-only posture that prevents the harness from teaching or protecting the user.
- Broad ceremony that does not produce insight, security, or evidence.

## yam Standard

```text
Direction before execution.
Context-reuse first.
Token-aware by default.
Start with momentum.
Deepen deliberately.
Basic direction fit and honest verification always.
Security first.
Explain what changed.
Honest by design.
Heavy proof when risk or user intent calls for it.
```
